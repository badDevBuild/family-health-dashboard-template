# 架构：一次写入，两种阅读方式

核心数据单元是一次健康事件 `HealthEvent`，例如一次体检或一次就医。每个事件包含多项 `Measurement`。指标可关联多个器官系统，因此同一份数据可以形成两个投影：

```text
原始报告
  -> HealthEvent + Measurement（事实存储）
       -> 时间轴：按日期查看事件
       -> 身体轴：按器官系统聚合指标与分析
```

## 模块边界

1. `reports/`：原始输入，只在本地或受控存储中存在。
2. `data/extracted/`：逐报告提取的事实层，不含诊断。
3. `data/analysis/`：按人汇总后的解释、趋势和标注为参考的关联。
4. `data/suggestions/`：复查和日常关注建议，止步于“咨询医生”。
5. `data/lifestyle/`：具体但非处方的生活指南。
6. `src/`：只读展示，不负责上传或修改健康数据。

## 为什么不让前端直接读报告

浏览器 bundle 很容易被缓存、复制或错误发布。后台管道先生成最小化的结构化结果，前端只接收展示所需字段；公开模板则只构建虚构数据。

## 状态边界

- `staged`：候选结果，尚未通过复核。
- `reviewed`：独立复核已返回，但人工/主 Agent 尚未逐项综合。
- `approved`：所有纠正已处理，可生成看板。
- `published`：已部署并完成读回验收。

这些状态不可互相替代。尤其不能把“模型调用成功”当成“内容已批准”，也不能把“本地构建成功”当成“线上发布成功”。
